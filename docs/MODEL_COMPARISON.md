# Сравнение Cutie, EfficientTAM-S, LiVOS и SAM 3.1

## Подготовка моделей

Все команды используют один `.venv`. Каждая команда `setup --model` получает только выбранные исходники и checkpoint:

```bash
uv run document-vos setup --model baseline
uv run document-vos setup --model finetuned
uv run document-vos setup --model efficienttam
uv run document-vos setup --model livos
uv run document-vos setup --model sam31
```

Существующие `setup` и `setup --sam` сохраняют прежнее поведение. Для SAM 3.1
нужен одобренный доступ к gated checkpoint `facebook/sam3.1` в Hugging Face и
авторизация через `hf auth login`. У LiVOS checkpoint находится в Google Drive.
Если издатель не опубликовал checksum, setup записывает SHA-256 первого
получения в соседний `.receipt.json`; повторное изменение файла будет обнаружено.
EfficientTAM-S checkpoint закреплён по Hugging Face commit, размеру и SHA-256.
Setup не загружает датасеты.

Для fine-tuned Cutie текущий каталог остаётся `UNPUBLISHED`: setup сообщит,
если Release-веса недоступны. Для личного checkpoint используйте `--weights`.

## Инференс

```bash
uv run document-vos infer --model efficienttam --sample
uv run document-vos infer --model livos --sample
uv run document-vos infer --model sam31 --sample
```

Как и для Cutie, поддерживаются `--input-dir` и `--manifest`. Собственные видео
сначала подготовьте через `document-vos prepare videos`; кадры и первая
непустая маска должны пройти существующую проверку входного каталога. Модели
получают одну и ту же начальную маску. Ground truth после инициализации модель
не получает.

EfficientTAM и SAM 3.1 требуют CUDA. LiVOS применяет штатное короткое измерение
480 пикселей; checkpoint загружается через `weights_only=True`, а неявная
загрузка ImageNet весов во время инференса заблокирована.

## Сравнение

```bash
uv run document-vos benchmark
uv run document-vos benchmark --models baseline finetuned livos
uv run document-vos benchmark --resolution native  # вернуть штатные размеры моделей
uv run document-vos benchmark --resume results/ПАПКА-БЕНЧМАРКА
```

По умолчанию используется `benchmark.selected` и общий validation split из
локальной подготовки. Внешний `--manifest` должен быть custom-манифестом для
`independent` либо сопровождаться `--split-dir`, подтверждающим validation.
Настройки расположены в `benchmark.models`; CLI переопределяет YAML, YAML —
значения по умолчанию. Запуск сохраняет разрешённый конфиг, артефакты каждого
участника, оценку, PNG-маски и HTML/JSON итог. Статус `PARTIAL` означает, что
не все выбранные модели завершили оценку; такой результат не следует считать
полным сравнением.

Метрики используют общий evaluator: J, DAVIS F, J&F, Boundary IoU, decay и
покадровые кривые. Первый кадр исключён из качества. Сравнитель проверяет
совпадение кадров, первой маски, набора оцениваемых кадров и версии протокола.
Основное среднее сохраняет схему кадры → видео → равные веса датасетов.

По умолчанию **только команда `benchmark`** применяет `benchmark.resolution: cutie`
(`--resolution cutie`). Все модели читают исходные RGB-файлы и получают размер
по правилу CUTIE: короткая сторона ограничена `inference.max_internal_size`
(обычно 480), без увеличения маленьких кадров и с сохранением пропорций.
Например, 1080×1920 превращается в 480×853. Изображение масштабируется через
bilinear `align_corners=false`, первая бинарная маска — через nearest-exact.
EfficientTAM и LiVOS дополняют этот размер до кратности 16 (480×864), SAM 3.1 —
до кратности 14 (490×854). Padding снимается до восстановления исходного размера
PNG. Поэтому одинаков размер содержимого; число пикселей с padding у SAM 3.1
немного отличается. `run.json → inference.geometry` сохраняет исходный,
масштабированный и дополненный размеры для каждой последовательности.

Прямоугольные сетки EfficientTAM/SAM 3.1 адаптируются в экземпляре predictor:
размеры масок, prompt grids и позиционные кодировки соответствуют прямоугольнику.
Исходники внешних checkout не меняются. Совместимость адаптации проверяется
полными AST-хешами выбранных методов закреплённых версий; изменение upstream
останавливает запуск с ошибкой. Внутри видео требуется постоянный размер кадров.
Разные `max_internal_size` у baseline/finetuned в общем профиле запрещены.

`benchmark.resolution: native` возвращает прежние размеры и путь подготовки
JPEG для directory API. Обычный `infer` сохраняет штатную политику разрешения,
даже если в YAML стоит `benchmark.resolution: cutie`. Старые результаты нельзя
продолжать после изменения профиля/исходников: нужен новый запуск.

Внешние модели отдают маски писателю итератором, без полного списка предсказаний
в адаптере. Общий профиль использует ограниченную CPU-предзагрузку оригиналов
(`runtime.queue_size`, половина `io_threads` на чтение), без перекодирования JPEG.
Это меняет входной путь относительно прежних JPEG-прогонов; для проверки качества
все участники нового общего профиля используют одни исходные RGB-файлы.
Подготовка/экспорт по-прежнему не входят в `model_seconds`, но входят в полный
таймер. Внутренняя память самой модели остаётся под управлением upstream.

EfficientTAM по умолчанию использует `compile: true`: это **`vos_optimized=True`**,
класс `EfficientTAMVideoPredictorVOS` и `torch.compile` всех штатных VOS-компонентов,
а не только image encoder. `compile: false` возвращает обычный predictor.
Фактический класс и флаг `vos_optimized` сохраняются в отчёте (upstream может
отключить компиляцию на неподдерживаемом устройстве). Прогрева вне таймера нет:
первая компиляция входит в время, поэтому короткий холодный прогон не является
измерением установившегося FPS. Precision и параметры памяти остаются отдельными
настройками; общий размер сам по себе не делает их одинаковыми.

## Разрешённые настройки

| Модель | Checkpoint | Внутренний размер | Precision/offload |
|---|---|---|---|
| Cutie baseline | `weights: null` использует каталог Cutie | `inference.max_internal_size` | общий `inference` |
| Cutie finetuned | `weights: null` использует каталог Cutie | `inference.max_internal_size` | общий `inference` |
| EfficientTAM-S | `weights/efficienttam/efficienttam_s.pt` | CUTIE в benchmark; штатный в infer/native | `amp`, `dtype`, `compile`, offload |
| LiVOS wmose-480p | `weights/livos/livos-wmose-480p.pth` | `max_internal_size: 480` | `amp` |
| SAM 3.1 Multiplex | `weights/sam31/sam3.1_multiplex.pt` | CUTIE в benchmark; штатный в infer/native | `amp`, `dtype`, `compile`, `use_fa3`, offload |

`paths.cutie` задаёт checkout CUTIE (по умолчанию `external/Cutie`).
`paths.external_models` независимо задаёт каталог закреплённых внешних моделей
(по умолчанию `.cache/external`); смена пути CUTIE не перемещает эти исходники.
Явный `benchmark.models.<model>.weights` имеет приоритет перед каталогом весов.
В рабочем `config.yaml` finetuned указывает на существующий checkpoint
`results/training-v2/official/documents_main_training_last.pth`, совпадающий
по SHA-256 с `cutie-document.pth` из каталога. Пути YAML разрешаются
относительно самого YAML. При `weights: null` используются каноническое имя
из каталога и проверка его SHA-256; автоматического поиска другого checkpoint нет.

Источники и закреплённые исходники хранятся в
`src/document_vos/resources/external_models.json`. Оценки и FPS сами по себе не
являются научным доказательством за пределами выбранных данных, checkpoint и
протокола.

## SAM 3.1: локальный mask bridge

Адаптер использует полный штатный `build_sam3_multiplex_video_predictor`
(detector + multiplex tracker) закреплённой ревизии
`f1647e8d0c1d280991f4d1b7d974c2704537fe66`. Локальный модуль
`document_vos.sam31` компенсирует две несовместимости этой ревизии:
`start_session` базового predictor передаёт неподдерживаемый
`offload_state_to_cpu`, а multiplex interactivity не реализует `add_mask`.
Исходники в `.cache/external/sam31` не изменяются.

Bridge v1 поддерживает только новую сессию, один GPU, объект `1` на кадре `0`
и непустую бинарную маску исходного размера. Кадр `0` здесь — первый кадр после
штатного отбора первой непустой аннотации. Маска передаётся непосредственно в
`tracker.add_new_masks` как `(1, H, W)`; преобразование в рамки, точки или
маски detector не применяется. Штатный tracker сам меняет внутренний размер.
Bridge регистрирует tracker state, metadata и действие `add`, выполняет memory
preflight и сохраняет conditioning mask и кэш первого кадра. Для остальных
кадров создаются пустые записи кэша: в этой ревизии `_build_sam2_output`
иначе отбрасывает tracker-маски при слиянии с ещё несуществующей записью.
Последующая
штатная instance propagation выбирается по action history; детектор остаётся
в модели и используется штатной подготовкой backbone features.

Поддерживается только `amp: true`, `dtype: bfloat16` — официальный predictor
и tracker сами открывают BF16 autocast. Другие precision-настройки и
`offload_state_to_cpu: true` отклоняются явно. `compile`, `use_fa3` и
`offload_video_to_cpu` сохраняют смысл. Асинхронная загрузка кадров отключена.
В `run.json` → `inference` записываются `mask_bridge_version`,
`initialization_type`, `effective_precision`, фактический `internal_resolution`
и `tracker_mask_input_resolution`.

При построении официальный builder сначала загружает общий checkpoint в
tracker, поэтому печатает detector-ключи как `Unexpected keys`. Затем он
загружает checkpoint в полную модель. Показанные предупреждением
`freqs_cis_real` / `freqs_cis_imag` — RoPE-буферы, вычисляемые конструктором
из `freqs_cis`. Проверяйте итоговый `status.json` и `error.log`; сами эти
предупреждения не означают, что smoke завершился ошибкой.

Propagation идёт вперёд от кадра `0`. Маска выбирается по `out_obj_ids == 1`;
корректный ответ без этого объекта означает пустую маску. Пропущенные,
повторные и выходящие за диапазон кадры, несовместимые размеры и несогласованные
ID/маски завершают запуск ошибкой. Маски имеют исходное разрешение. Сессия
закрывается и при исключениях/OOM; при освобождении predictor его autocast
контексты закрываются в обратном порядке. Ошибка cleanup не заменяет исходную
ошибку инференса.

Перед полным validation выполните короткую проверку на пяти последовательных
локальных кадрах с настоящим checkpoint. Для того же split, что использовался
в прежнем многомодельном запуске:

```bash
uv run python -m document_vos.sam31_smoke --manifest data/split-v2/validation.jsonl --split-dir data/split-v2
```

Она создаёт новую папку `results/sam31-smoke-*`: `status.json`, при успехе пять
PNG и исходную маску, при ошибке `error.log`. Проверяет отсутствие сессий и
восстановление autocast. При занятой GPU сразу выходит с кодом `2` и статусом
`SKIPPED_GPU_BUSY`, без ожидания. Только после статуса `COMPLETE` запускайте:

```bash
uv run document-vos benchmark --models sam31 --manifest data/split-v2/validation.jsonl --split-dir data/split-v2
```

Новая папка benchmark создаётся автоматически. Эти явные параметры закрепляют
прежний validation split; без них CLI использует штатный путь подготовки из
конфига. При OOM сохраняйте статус и диагностику, не уменьшайте автоматически
данные, разрешение или модель. Успех отдельного SAM 3.1 validation не меняет
статус `PARTIAL` старого многомодельного сравнения. Тесты и проверка реальных
классов с подставными вычислениями подтверждают API и переходы состояния;
GPU smoke и завершённая validation-оценка проверяются отдельно.

## CPU-профиль и измерение скорости

Все модели используют общий `runtime.cpu_profile: p6-smt12`. Это шесть
физических ядер с двумя SMT-потоками на ядро, выбранные по Linux-топологии
в пределах доступной affinity. На текущем ноутбуке это CPU `0–11` с парами
`(0,5)`, `(1,2)`, `(3,4)`, `(6,7)`, `(8,9)`, `(10,11)`. Если шесть полных
пар недоступны, запуск завершается ошибкой. Автоматической замены профиля нет.
Affinity применяется до создания пулов; потоки и дочерние процессы наследуют
тот же набор CPU. Уже импортированные библиотечные пулы также настраиваются.

Значения по умолчанию: CPU workers — **6**, DataLoader workers — **6**,
I/O threads — **4**, PyTorch основного процесса — **6 intra-op / 1 inter-op**.
BLAS, OpenCV и вычислительные пулы CPU-воркеров используют **1 поток**.
Двенадцать означает доступные аппаратные потоки CPU, а не размер каждого
библиотечного пула. Переменные окружения задаются до импорта библиотек,
фактические пулы — после импорта. Callback штатного DataLoader для seed
сохраняется. Диагностические overrides числа workers допускаются, но такие
FPS получают `INCOMPATIBLE` для общего профиля.

`run.json` сохраняет запрошенные значения в `runtime`, фактическую affinity,
физические ядра, пулы библиотек и числа воркеров в `cpu_runtime`. SAM smoke
сохраняет тот же блок в `status.json`; обучение — также в `runtime.json`.

Протокол `document-vos/compute-v3` сохраняет существующие поля `model_seconds`,
`full_seconds`, `model_fps`, `full_fps` и добавляет версию и границы измерений:

| Модель | Граница `model_seconds` |
|---|---|
| CUTIE baseline/finetuned | Существующий `InferenceCore.step`, без изменений |
| LiVOS | `InferenceCore.step` |
| EfficientTAM | `forward_image`, `track_step`, `_encode_new_memory` |
| SAM 3.1 | `run_backbone_and_detection`, `tracker.forward_image`, `tracker.track_step`, `tracker._encode_new_memory` |

Каждый внешний compute-вызов окружён синхронизацией CUDA. Вложенные вызовы
одного таймера учитываются один раз. Вычисления первого кадра, включая
кодировщик и memory preflight, включены; дополнительного warmup нет.
Локальные обёртки устанавливаются только на время обработки последовательности
и восстанавливают методы закреплённого upstream API даже при ошибке.

`full_seconds` включает обработку последовательностей, чтение и преобразование
входов, подготовку JPEG там, где этого требует API, очистку временного кэша,
экспорт масок до завершения всех записей PNG и финальную синхронизацию CUDA.
CUTIE сохраняет свою схему чтения/записи с общим бюджетом четырёх I/O-потоков.
LiVOS читает исходные изображения без промежуточного JPEG. Загрузка checkpoint,
предварительная проверка/хеширование входов, evaluator и визуализация исключены.

JSON/HTML/CSV показывают совместимость скорости отдельно от совместимости
качества. Начиная с `document-vos/benchmark-fps-v1`, каждый участник сохраняет
подписанный хешем общий план: политику разрешения, версию адаптера, входной
конвейер, исходники, настройки всех выбранных моделей и runtime. Отдельно
подписываются фактически применённые настройки, геометрия последовательностей,
версия PyTorch/CUDA, GPU и TF32. Проверка сверяет подписи, план и настройки
участника, проверяет фактическое масштабирование и padding по правилу CUTIE,
сравнивает размеры содержимого между внешними моделями и настройки повторов
одной модели. Различный padding до stride 14 и 16 допустим.
Результаты без подписи, результаты разных планов или разных входов и
начальных масок несовместимы по FPS.
`COMPATIBLE` означает совместимость зафиксированного плана измерения и среды,
но разные модели внутри этого плана всё ещё могут использовать разные precision,
TF32, алгоритмы памяти и padding; равная вычислительная нагрузка не подразумевается.

Для ограниченного исследования геометрии можно запустить:

```bash
TORCHINDUCTOR_CACHE_DIR="$(mktemp -d)" uv run python -m document_vos.geometry_profile \
  --model efficienttam --frames 12 --output results/geometry-profile-efficienttam
```

Для SAM 3.1 выберите `--model sam31` и другую папку вывода. Диагностика
выполняет два размеченных клипа разной
ориентации и повторяет их в одном процессе, сохраняя маски, evaluator, снимки и
время. Для холодной компиляции укажите новый пустой `TORCHINDUCTOR_CACHE_DIR`.
Повторный проход и время после первого выданного кадра — отдельная диагностика,
а не замена основного FPS: первая компиляция остаётся внутри основного таймера.
У SAM выдача масок может буферизоваться, поэтому разницу между моментами выдачи
нельзя автоматически считать временем отдельного кадра.

Старые результаты без фактического профиля или с иной границей
таймера отмечаются `INCOMPATIBLE`: сохранённые FPS остаются историческими
измерениями, сравнение скорости по ним не выполняется. Совместимые метрики
качества и их дельты сохраняются. `--resume` проверяет версию таймера,
фактический CPU-профиль, конфиг, входы, исходники и артефакты завершённых этапов.
При несовпадении нужен новый запуск; исторические артефакты не переписываются.

Этот профиль выбран для задачи; доказательство его оптимальности и полный
GPU-бенчмарк в проверку реализации не входят.
